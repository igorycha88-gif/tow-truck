## 1. Цели и задачи

### 1.1 Бизнес-цель
Подключить эвакуация.online к централизованному мониторингу (VPS 130.49.129.241):
видеть в общих дашбордах доступность сайта, бизнес-метрики (посетители/заявки/
конверсия), метрики приложения, сервера и PostgreSQL — без открытия новых портов.

### 1.2 Пользовательская ценность
Владелец в единой Grafana мониторинга видит эвакуация.online рядом с da-dryclean.ru:
дашборды «Обзор сайта», «Все сайты», «Бизнес сайта»; алерты SiteDown/SiteNoTraffic
приходят в общий Telegram.

### 1.3 Метрики успеха
- 4 эндпоинта метрик отвечают 200 по ключу `X-Monitoring-Key`
- Без ключа — 403; новые порты наружу не открываются
- После подключения мониторингом: `monitoring_site_metrics_up{site="эвакуация.online",kind=...}=1`

## 2. Контракт взаимодействия (ADR-007 мониторинга, обязательно к соблюдению)

| Параметр | Значение |
|---|---|
| Пути | `GET https://эвакуация.online/metrics/{tracking,content,node,postgres}` |
| Auth | Заголовок `X-Monitoring-Key: <64 hex>`; неверный/отсутствующий → **403** |
| Методы | Только `GET` (иначе 403/405) |
| Rate limit | 10 r/s на location'ы `/metrics/` |
| Формат | Prometheus text exposition, `Content-Type: text/plain; version=0.0.4` |
| Канал | Только публичный HTTPS (443). Новых открытых портов НЕТ |

Значение ключа передаёт владелец через защищённый канал (тот же общий секрет,
что у мониторинга и da-dryclean). Ключ НЕ попадает в git, коммиты, логи, ЧТЗ.

До подключения мониторинга ответы `404` — норма (мониторинг увидит `up=0`).

## 3. Функциональные требования

### US-001: Бизнес-метрики (tracking)
- GIVEN мониторинг вызывает `GET /metrics/tracking` с корректным ключом
- WHEN запрос обработан
- THEN ответ 200 и присутствуют `business_*`-метрики из БД `tow_truck` (см. §4.1)

### US-002: Защита эндпоинтов
- GIVEN запрос без ключа или с неверным ключом, или не-GET
- WHEN запрос достигает nginx
- THEN ответ 403 (не-GET допускается 405), в логах ключ не раскрывается

### US-003: Серверные метрики (node)
- GIVEN запрос `GET /metrics/node` с ключом
- THEN 200 и метрики `node_*` (node_exporter)

### US-004: Метрики PostgreSQL
- GIVEN запрос `GET /metrics/postgres` с ключом
- THEN 200 и метрики `pg_*` (postgres_exporter, readonly-пользователь)

### US-005: Метрики приложения (content)
- GIVEN запрос `GET /metrics/content` с ключом
- THEN 200 и `content_http_requests_total{method,route,code}`,
  `content_http_request_duration_seconds{method,route}` (route — шаблон пути,
  не сырой URL)

## 4. Спецификация метрик

### 4.1 `business_*` — tracking (гейджи, окна 24ч/1ч, пересчёт из БД раз в 60 с, кэш в памяти)

| Метрика | Источник данных (Prisma/`tow_truck`) |
|---|---|
| `business_sessions_active` | активные сессии за последние 30 мин (Visit) |
| `business_page_views_24h`, `business_page_views_1h` | COUNT(Visit) за окно |
| `business_unique_visitors_24h` | COUNT(DISTINCT ip) Visit за 24ч |
| `business_sessions_24h` | сессии за 24ч (по ip+окну 30 мин или sessionStorage-логике сайта) |
| `business_avg_session_duration_seconds_24h` | средняя длительность сессии |
| `business_bounce_rate_24h` | доля однократных просмотров (0..1) |
| `business_events_24h{event_type}` | клики/события (Click и др.), ≤ 20 значений лейбла |
| `business_leads_24h`, `business_leads_1h` | заявки (Order, все статусы) |
| `business_conversion_rate_24h` | leads_24h / sessions_24h (0..1, деление на 0 → 0) |
| `business_service_clicks_24h{service}` | клики по услугам, топ-20 |
| `business_referral_sources_24h{source}` | только если фиксируется referer, топ-10 + `other` |
| `business_geo_visitors_24h{city}` | только если есть гео-данные, топ-10 + `other` |

Правила:
- Метрики без данных в БД сайта (referer/geo не фиксируются) — не отдаются вообще
  (не отдавать нули для несуществующих разрезов).
- Кардинальность: `event_type` ≤ 20, `service` ≤ 21 (топ-N + `other`), `city` ≤ 11.
- Существующие counter'ы трекинга сайта (если есть `tracking_events_total`) —
  остаются как есть, отдаются там же.
- Все запросы к БД — с индексами по `createdAt` (проверить план, без seq scan на
  больших таблицах).

### 4.2 `content_*` — метрики приложения (Next.js, prom-client)
- `content_http_requests_total{method,route,code}` — counter
- `content_http_request_duration_seconds{method,route}` — histogram
  (`_bucket/_sum/_count`; базовое имя сохранить)
- `route` — нормализованный шаблон (`/uslugi/[slug]`, не сырой path), ≤ 100 значений
- Сбор — middleware/инструментация Next.js; сами пути `/metrics/*` в метрики
  приложения не включать (или помечать и исключить).

### 4.3 node_exporter
- Версия ≥ 1.x, systemd-сервис, слушает **только 127.0.0.1:9100**
- Не контейнер (паттерн эталона), collector'ы по умолчанию

### 4.4 postgres_exporter
- Docker-контейнер в compose сайта, слушает **только 127.0.0.1:9187**
- Отдельный readonly-пользователь БД с ролью `pg_monitor` (НЕ суперпользователь)
- DSN — только в `.env` сайта (chmod 600), не в compose/git

## 5. Инфраструктура (nginx сайта)

1. `/etc/nginx/conf.d/monitoring-key.conf` (chmod 600, владелец root):
   ```nginx
   map $http_x_monitoring_key $metrics_auth { default 0; "<КЛЮЧ>" 1; }
   ```
2. В server-блоке сайта (443):
   ```nginx
   limit_req_zone $binary_remote_addr zone=metrics_limit:10m rate=10r/s;

   location ^~ /metrics/tracking {
     limit_except GET { deny all; }
     if ($metrics_auth = 0) { return 403; }
     limit_req zone=metrics_limit burst=5 nodelay;
     proxy_pass http://<upstream приложения>/metrics/tracking;
   }
   # аналогично: /metrics/content → <upstream приложения>
   #              /metrics/node     → http://127.0.0.1:9100
   #              /metrics/postgres → http://127.0.0.1:9187
   ```
3. Blue-Green: проксировать через **именованный upstream** приложения (тот же,
   что использует сайт), чтобы переключение релизов не ломало эндпоинты.
4. Ключ не добавлять в log_format; access_log для `/metrics/` можно вынести в
   отдельный файл с минимальным форматом.
5. `nginx -t` → reload; проверить, что основной сайт и `/api/health` работают.

## 6. Нефункциональные требования

- Безопасность: ключ только в `monitoring-key.conf` (600) и при необходимости в
  `.env` приложения; пароль root сервера не хранить в репозитории/документах.
- Производительность: пересчёт гейджей не чаще 1 раза в 60 с (кэш), БД-запросы
  по индексам; Prometheus скрейпит раз в 15–60 с — нагрузка минимальна.
- Совместимость: формат Prometheus text 0.0.4, имена метрик — точно как в §4
  (централизованные дашборды и алерт `SiteNoTraffic` используют
  `business_page_views_24h`).

## 7. Декомпозиция на задачи

### Backend
- **TASK-BCK-001** Route handler `/metrics/tracking`: business_* гейджи из
  Prisma, кэш 60 с, окна 24ч/1ч, нормализация IP. ~4 ч
- **TASK-BCK-002** prom-client в Next.js: middleware + `/metrics/content`,
  route-шаблоны. ~3 ч
### Testing
- **TASK-TST-001** Vitest: расчёт гейджей (happy path, пустая БД → нули,
  окна, кардинальность топ-N+other, деление на 0). ~2 ч
- **TASK-TST-002** Проверки контракта: 200 с ключом / 403 без / не-GET,
  формат text/plain. ~1 ч
### Infrastructure
- **TASK-INF-001** node_exporter (systemd, 127.0.0.1:9100). ~1 ч
- **TASK-INF-002** postgres_exporter (docker, 127.0.0.1:9187, pg_monitor). ~1.5 ч
- **TASK-INF-003** nginx: key-map, 4 location, rate limit, upstream, reload. ~1.5 ч

Порядок: BCK → TST → INF; выкатка на прод — через штатный prod-деплой сайта.

## 8. Критерии приёмки

1. `curl -H "X-Monitoring-Key: <ключ>" https://эвакуация.online/metrics/tracking`
   → 200, `text/plain`, содержит `business_page_views_24h` и `business_leads_24h`.
2. Без ключа/с неверным ключом → 403 на всех 4 путях; `POST` → 403/405.
3. `/metrics/node` отдаёт `node_*`, `/metrics/postgres` отдаёт `pg_*`,
   `/metrics/content` отдаёт `content_http_requests_total`.
4. `ss -tlnp` на сервере: 9100 и 9187 слушают только 127.0.0.1 (наружу закрыто).
5. `grep -r "<ключ>" src/ deploy/` — пусто (ключ не в git).
6. Vitest/линты проекта — зелёные.
7. Регрессия: сайт отвечает 200, `/api/health` → 200, Grafana сайта
   (`/grafana`) работает после правок nginx.
8. (После подключения мониторингом) `monitoring_site_metrics_up{site="эвакуация.online"}=1`
   для всех 4 kind и данные на дашборде «Бизнес сайта».

## 9. Риски и зависимости

- Blue-Green смена портов приложения → проксировать через именованный upstream (§5.3).
- Отсутствие referer/geo в модели данных → соответствующие метрики не отдаются (§4.1).
- IDN-домен: HTTPS уже настроен; если у Prometheus мониторинга возникнут проблемы
  с юникод-хостом — мониторинг переключится на punycode `xn--80akhbyknj4f.online`
  (на стороне сайта изменений не требуется).
