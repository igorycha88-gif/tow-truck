## 1. Цели и задачи

### 1.1 Бизнес-цель
Визуализировать ключевые бизнес-метрики сервиса эвакуации в Grafana для мониторинга
конверсии и операционной эффективности.

### 1.2 Пользовательская ценность
Оператор/владелец видит в реальном времени:
- количество посетителей (уникальные IP/день)
- количество заявок (по статусам)
- клики по номеру телефона

### 1.3 Метрики успеха
- Grafana доступна по `https://эвакуация.online/grafana`
- Дашборд обновляется не реже 1 раза в минуту
- Базовая аутентификация (admin/кастомный пароль)

## 2. Функциональные требования

### 2.1 User Stories

**US-001:** Как оператор, я хочу видеть количество посетителей за день/неделю/месяц,
чтобы оценивать трафик.

**US-002:** Как оператор, я хочу видеть количество заявок по статусам (NEW, CALLED, DONE,
CANCELLED), чтобы понимать конверсию воронки.

**US-003:** Как оператор, я хочу видеть количество кликов по номеру телефона,
чтобы оценивать эффективность CTA.

**US-004:** Как администратор, я хочу получить доступ к Grafana по защищённому URL
с базовой аутентификацией.

## 3. Нефункциональные требования

### 3.1 Производительность
- Метрики не должны замедлять API (запросы к БД асинхронные)
- Dashboard load time < 3s

### 3.2 Безопасность
- Grafana за Nginx reverse proxy с HTTPS
- Базовая аутентификация (username/password)
- Нет доступа к Grafana извне без авторизации

### 3.3 Доступность
- Grafana на пути `/grafana`
- Автоматический healthcheck

### 4.2 Решение Архитектора (ADR-001)

**Выбран вариант:** PostgreSQL datasource plugin (прямой доступ Grafana к БД).

**Обоснование:**
- MVP требует быстрой реализации
- PostgreSQL уже развернут и доступен
- Grafana native поддерживает PostgreSQL
- Минимальный дополнительный код

**Альтернативы отклонены:**
- JSON API datasource (больше кода, избыточно для MVP)
- Prometheus exporter (избыточно для масштаба проекта)

### 4.3 Схема данных (метрики из PostgreSQL)

**Количество посетителей:**
```sql
-- Уникальные IP за период (из таблицы Order + rate-limit логи)
SELECT DATE(createdAt) as date, COUNT(DISTINCT ip) as unique_visitors
FROM "Order"
WHERE createdAt >= NOW() - INTERVAL '30 days'
GROUP BY DATE(createdAt)
ORDER BY date;
```

**Количество заявок по статусам:**
```sql
SELECT DATE(createdAt) as date, status, COUNT(*) as count
FROM "Order"
WHERE createdAt >= NOW() - INTERVAL '30 days'
GROUP BY DATE(createdAt), status
ORDER BY date, status;
```

**Клики по номеру:**
```sql
-- Из логов приложения или отдельной таблицы click_events
-- Требуется добавить логирование кликов в Application
```

### 4.4 Изменения в БД

**Требуется новая таблица `ClickEvent`:**
```prisma
model ClickEvent {
  id        String   @id @default(cuid())
  ip        String?
  userAgent String?
  page      String   @default("home")
  createdAt DateTime @default(now())

  @@index([createdAt])
}
```

### 4.5 API endpoints

**POST /api/click-event** — логирование клика по номеру (ОБЯЗАТЕЛЬНО)
```json
Request: { "page": "home" }
Response: 201 { "id": "..." }
```

**GET /api/metrics** — агрегированные метрики (ОПЦИОНАЛЬНО, для кэширования/доп. целей)
```json
Response: {
  "visitors": { "today": 42, "week": 300, "month": 1200 },
  "orders": { "today": 5, "week": 35, "month": 140 },
  "clicks": { "today": 12, "week": 85, "month": 400 }
}
```

> **Примечание:** Grafana будет запрашивать данные напрямую из PostgreSQL через
> datasource plugin. Endpoint `/api/metrics` опционален и может быть реализован
> для мобильного приложения или кэширования.

## 8. Риски и зависимости

### Риски:
1. **Производительность БД:** Запросы агрегации могут замедляться при большом объеме данных
   - Решение: индексы, materialized views, кэширование
2. **Безопасность Grafana:** Публичный доступ без аутентификации
   - Решение: обязательная базовая аутентификация + Nginx
3. **Размер данных:** Логи кликов могут расти быстро
   - Решение: партиционирование по дате, очистка старых записей

### Зависимости:
- Существующая PostgreSQL (Order table)
- Docker и docker-compose
- Nginx (уже настроен для prod)
