## 1. Цели и задачи

### 1.1 Бизнес-цель
Полностью подключить эвакуация.online к централизованному мониторингу на VPS
130.49.129.241: видеть в Grafana доступность, бизнес-метрики, метрики приложения,
сервера, БД и поисковой выдачи рядом с da-dryclean.ru — без открытия новых портов
и без хранения секретов в репозитории.

### 1.2 Пользовательская ценность
Владелец в единой Grafana видит:
- дашборд «Бизнес сайта» — посетители/заявки/конверсия;
- дашборд «Обзор сайта» — uptime, TLS, сервер (ЦП/память/диск), PostgreSQL;
- дашборд «Вебмастер» — топ поисковых запросов, показы/клики по дням;
- алерты SiteDown / SiteNoTraffic / SiteMetricsEndpointDown в общем Telegram.

### 1.3 Метрики успеха
- Все 5 источников данных доступны и собираются мониторингом;
- `monitoring_site_metrics_up{site="эвакуация.online",kind=...}=1` для всех 4 kind;
- `monitoring_site_visits_total` и `monitoring_search_*{site="эвакуация.online"}` присутствуют в Prometheus;
- новых открытых портов нет; секреты только в `.env`/`monitoring-key.conf` (chmod 600).

## 4. Оставшиеся задачи (только node + postgres)

### 4.1 node_exporter (kind=node)
1. Установить `node_exporter` (пакет или бинарник).
2. Биндить **строго на `127.0.0.1:9100`** (systemd-юнит, `--web.listen-address=127.0.0.1:9100`).
3. Проверка: `curl -s http://127.0.0.1:9100/metrics | head` — текст Prometheus, метрики `node_*`.

### 4.2 postgres_exporter (kind=postgres)
1. Развернуть `postgres_exporter` (docker или бинарник), порт **`127.0.0.1:9187`**.
2. Создать readonly-пользователя БД с ролью `pg_monitor` (НЕ суперпользователь).
3. DSN — только в `.env` экспортёра (chmod 600), не в compose/git.
4. Проверка: `curl -s http://127.0.0.1:9187/metrics | head` — метрики `pg_*`.

### 4.3 nginx — два новых location
По аналогии с уже работающими `/metrics/tracking` и `/metrics/content`:

```nginx
location = /metrics/node {
    limit_except GET { deny all; }
    if ($metrics_auth = 0) { return 403; }
    limit_req zone=metrics_limit burst=5 nodelay;
    proxy_pass http://127.0.0.1:9100/metrics;
}

location = /metrics/postgres {
    limit_except GET { deny all; }
    if ($metrics_auth = 0) { return 403; }
    limit_req zone=metrics_limit burst=5 nodelay;
    proxy_pass http://127.0.0.1:9187/metrics;
}
```

Требования к защите (единые для всех `/metrics/*` сайта):
- Заголовок `X-Monitoring-Key`: неверный/отсутствующий → **403**.
- Только метод **GET**.
- Rate limit ≤ 10 r/s (мониторинг опрашивает ~1 раз в 60 с).
- Экспортёры 9100/9187 — только localhost; в файрволе порты НЕ открывать.

## 5. Декомпозиция на задачи

### Infrastructure (на стороне сайта)
- **TASK-INF-001** node_exporter (systemd, 127.0.0.1:9100). ~1 ч
- **TASK-INF-002** postgres_exporter (docker, 127.0.0.1:9187, pg_monitor). ~1.5 ч
- **TASK-INF-003** nginx: 2 новых location `/metrics/node`, `/metrics/postgres`
  (key-map уже есть для tracking/content — переиспользовать), reload. ~0.5 ч

Порядок: INF-001/002 параллельно → INF-003 → уведомить команду мониторинга.
Выкатка — через штатный prod-деплой/SSH сайта.

## 6. Критерии приёмки

```bash
KEY=<персайтный ключ эвакуация.online>

# 1. С ключом — 200 и метрики:
curl -s -o /dev/null -w '%{http_code}\n' -H "X-Monitoring-Key: $KEY" \
  https://эвакуация.online/metrics/node        # 200, содержит node_*
curl -s -o /dev/null -w '%{http_code}\n' -H "X-Monitoring-Key: $KEY" \
  https://эвакуация.online/metrics/postgres    # 200, содержит pg_*

# 2. Без ключа / с неверным ключом — 403:
curl -s -o /dev/null -w '%{http_code}\n' https://эвакуация.online/metrics/node       # 403
curl -s -o /dev/null -w '%{http_code}\n' -H "X-Monitoring-Key: wrong" \
  https://эвакуация.online/metrics/postgres  # 403

# 3. Экспортёры слушают только localhost:
ss -tlnp | grep -E '9100|9187'   # только 127.0.0.1

# 4. Ключ не в git:
grep -r "<КЛЮЧ>" src/ deploy/   # пусто
```

После деплоя уведомить команду мониторинга — она проверит:
- `monitoring_site_metrics_up{site="эвакуация.online",kind="node|postgres"} = 1`
- появление метрик `node_*` / `pg_*` в Grafana (дашборд «Обзор сайта»)
- уход алерта `SiteMetricsEndpointDown{kind=node|postgres}` в Resolved

## 7. Что НЕ входит в это ЧТЗ

- **Метрика и Вебмастер** — уже подключены на стороне мониторинга; от сайта не требуется ничего.
- **Изменения на стороне мониторинга** — не требуются: `metrics_urls` для всех 4 kind
  уже прописаны в `config/sites.yml`, SD подхватит эндпоинты автоматически в течение 60 с
  после их появления.
- **Новые порты наружу** — запрещены (см. §3.1 и AGENTS.md мониторинга, правило изоляции).

## 9. Риски и зависимости

- **Blue-Green смена портов приложения** — `/metrics/tracking` и `/metrics/content`
  проксировать через именованный upstream приложения (см. ЧТЗ_Централизованный_мониторинг §5.3).
- **IDN-домен** — HTTPS уже настроен; при проблемах с юникод-хостом мониторинг
  переключится на punycode `xn--80aae0ai8cwa4cza.online` (на стороне сайта изменений не требуется).
- **postgres_exporter и версия PostgreSQL** — проверить совместимость; DSN с
  readonly-пользователем `pg_monitor` (не superuser).
- **node_exporter под systemd** — предпочтительнее контейнера (паттерн эталона);
  collector'ы по умолчанию достаточно.
