# ЧТЗ — Блок «Адреса» в форме заявки (Откуда/Куда) + отправка по SMTP

- **Дата:** 2026-08-31
- **Статус:** Утверждено (ответы пользователя получены)
- **Маршрут:** 1 — Стандартная задача (Аналитик → Разработчик → Тестировщик → DevOps)
- **Исполнитель после ЧТЗ:** Разработчик

## 1. Контекст

Сейчас форма заявки (`src/components/forms/OrderForm.tsx`) содержит одно адресное поле
`location` («Адрес или район подачи»). Заявка сохраняется в БД (Prisma, модель `Order`)
и отправляется операторам в Telegram + на почту через Яндекс SMTP
(`src/lib/mailer.ts`, `src/services/notifyService.ts`). SMTP уже настроен и работает.

## 2. Задача

Заменить одиночное поле «Адрес или район подачи» на блок **«Адреса»** с двумя полями:

1. **«Откуда забрать»** — обязательное.
2. **Куда доставить»** — необязательное (часто нужна только вытащить машину, без доставки).

Оба адреса: сохранять в БД + отправлять в письме по SMTP и в Telegram.
Пустое «Куда доставить» в уведомлениях не показывается.

## 3. Решения пользователя (зафиксированы)

| Вопрос | Решение |
|--------|---------|
| Обязательность «Куда доставить» | Необязательное |
| Старое поле `location` | Заменить на блок «Адреса» (два поля) |
| Хранение | Сохранять в БД (миграция Prisma) |

## 4. Архитектурное решение (мини-ADR, без привлечения Архитектора)

Замена полей — механическая, новых сущностей/enum/API-контекстов нет.
Решение по БД (стандартный паттерн expand → backfill → contract):

1. Добавить `addressFrom String?`, `addressTo String?` в модель `Order`.
2. Бэкфилл: `UPDATE "Order" SET "addressFrom" = location` (пустые → `'Не указан'`).
3. `addressFrom` → `NOT NULL`; колонку `location` удалить.
4. Dev: миграция через `prisma migrate dev` (или db push + ручной SQL-бэкфилл);
   Prod: `prisma migrate deploy`.

Именование полей: `addressFrom` / `addressTo` (в БД, Zod, сервисах, форме).

## 5. Требования

### 5.1 БД (Prisma)

- `Order.addressFrom String` — NOT NULL (откуда забрать).
- `Order.addressTo String?` — nullable (куда доставить).
- `Order.location` — удалить, данные перенести в `addressFrom` (см. §4).
- Миграция не должна терять существующие заявки.

### 5.2 Валидация (Zod, `src/lib/validators/order.ts`)

- `addressFrom`: trim, обязательное, 3–200 символов → сообщение
  «Укажите адрес, откуда забрать автомобиль».
- `addressTo`: trim, необязательное, макс. 200 символов; пустая строка → `undefined`.
- `location` из схемы удалить.

### 5.3 Форма (`OrderForm.tsx`)

- Визуальный блок «Адреса» (заголовок/legend), под ним два поля:
  - «Откуда забрать» — Input, placeholder вида «Например: МКАД 50 км, внешняя сторона».
  - «Куда доставить» — Input, placeholder вида «Например: Москва, ул. Тверская 1 (необязательно)».
- Старое поле «Адрес или район подачи» удалить.
- Ошибки валидации отображаются как у остальных полей (`FieldError`).

### 5.4 API и сервисы

- `POST /api/orders` — без изменений логики (спред валидированных данных).
- `ordersService.createOrder` — сохранять `addressFrom`, `addressTo`.
- `mailer.ts` (SMTP-письмо, text+html) — строки:
  «Откуда забрать: …» и «Куда доставить: …» (вторая — только если заполнено).
- `notifyService.ts` (Telegram) — те же строки, экранирование HTML сохранить.
- `src/types/index.ts` — `OrderInput`/`OrderRecord`: `location` → `addressFrom`, `addressTo?`.

### 5.5 Логирование (Правило 8)

- Логирование в изменённых файлах сохранить/дополнить контекстом `addressFrom`
  (в ordersService — вместо `location`).

## 6. Критерии приёмки

1. В форме есть блок «Адреса» с полями «Откуда забрать» (обязательное) и
   «Куда доставить» (необязательное); старое поле удалено.
2. Отправка заявки только с заполненным «Откуда забрать» (3–200 симв.); «Куда
   доставить» можно оставить пустым (до 200 симв.).
3. Заявка сохраняется в БД: `addressFrom` заполнено, `addressTo` — если указано.
4. Существующие заявки не потеряны: `location` перенесён в `addressFrom`.
5. SMTP-письмо содержит оба адреса (или только заполненные).
6. Telegram-уведомление содержит оба адреса (или только заполненные).
7. `npm run test && npm run lint && npx tsc --noEmit` — без ошибок.
8. Автотесты обновлены (unit: validator, mailer, notifyService, ordersService,
   route; e2e: home.spec.ts), покрытие новых изменений ≥ 60%.
